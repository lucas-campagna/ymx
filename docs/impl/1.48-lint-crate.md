description: |
  Adds a side-effect-free static analyzer as a new I/O-free ymx-lint crate. It
  consumes a loaded Project, Options, and a LintConfig extracted from the entry
  file's _ymx.lint (CLI --deny/--allow/--fail-on override), and reports advisory
  L### findings in diagnostics or JSON form. The CLI lint branch forces a static
  mode with no shell executor and no IPC host, so sh/pw payloads and IPC aliases
  are analyzed but never executed. Compiler E### diagnostics are reported
  separately from L### findings; no E### code is added or changed. See
  docs/PRD/16-linting.md.

# 1.48 — Static linter (ymx-lint + CLI lint mode)

## Task 1: ymx-lint crate skeleton (ymx-lint)

- [x] 1.1 Add a new `crates/ymx-lint` crate to the workspace (edition 2021); library target depends on `ymx-core` and `ymx-config` only — no normal `ymx-lib`, `ymx-test`, or `ymx-cli` dependency; `ymx-lib` is allowed as a `[dev-dependencies]` entry for integration tests only (no cycle: `ymx-lib` does not depend on `ymx-lint`)
- [x] 1.2 Define `LintSeverity { Error, Warning, Info }`, `FailOn { Error, Warning, Info, None }`, and `LintConfig { deny, allow, fail_on }` in `ymx-config` and re-export them from `ymx-lint`; define `LintDiagnostic { code, severity, file, line, col, component, message, help }` and `LintReport { findings, diagnostics }` in `ymx-lint`
- [x] 1.3 Implement the pure entry point `lint_project(&Project, &Options, &LintConfig) -> LintReport` — no I/O, no mutation of the input `Project`/`Options`
- [x] 1.4 Implement `LintDiagnostic` rendering: `[L001] warning: file:line:col (component): message` with an optional indented `  help: ...` line; compiler diagnostics in the report render as `[compile E###] ...`
- [x] 1.5 Implement JSON emission with separate `findings` (L###) and `diagnostics` (E###) arrays plus a `summary` counting L### findings only
- [x] 1.6 Source all reference sites from existing `ymx-core` parsers (call-site grammar, string interpolation, math, `ParsedKey`, `from` values); add read-only core accessors if needed — no second YAML parser or regex scanner in `ymx-lint`

### Acceptance criteria

- [x] `cargo build -p ymx-lint` succeeds with no filesystem, process, or network imports in the crate
- [x] `lint_project` is deterministic: identical inputs produce byte-identical `LintReport` output
- [x] No `E###` code is added, renamed, or given new meaning

## Task 2: LintConfig extraction (ymx-config)

- [x] 2.1 Parse `_ymx.lint` from the **entry file's** `_ymx` only; non-entry `_ymx` blocks remain completely ignored (never parsed or validated)
- [x] 2.2 Recognize `deny`, `allow`, and `fail_on`; defaults are `[]`, `[]`, and `error` respectively
- [x] 2.3 Report `E010` for unknown fields inside `_ymx.lint`, wrong types, unknown L-codes, invalid `fail_on` values, and a code present in both `deny` and `allow`
- [x] 2.4 Apply CLI > entry-file > default precedence for `--deny`, `--allow`, and `--fail-on`
- [x] 2.5 Place the extraction helper in `ymx-config` (a small entry-file-only helper is acceptable if it does not move `_ymx` interpretation into `ymx-lib` and does not introduce a reverse dependency on `ymx-lint`)

### Acceptance criteria

- [x] A non-entry file with a malformed or unknown `_ymx.lint` does not affect the lint run
- [x] Invalid entry-file `_ymx.lint` fails with `E010` before analysis begins
- [x] CLI flags override the entry-file values; `ymx-lib` gains no `_ymx`/`_test`/lint logic

## Task 3: Static compile check (ymx-lint, ymx-cli)

- [x] 3.1 Force `options.executor = None` and `options.ipc = None` on a local copy of `Options` before the static compile check, regardless of caller values
- [x] 3.2 Ensure the CLI lint branch does not construct `StdExecutor` or `StdIpcHost`
- [x] 3.3 Still visit `$sh`/`$pw` call sites, shell payloads, IPC alias declarations, and IPC alias calls so they feed the call graph and L005/L006
- [x] 3.4 Capture compiler E### diagnostics from the static check into `LintReport::diagnostics`, separate from `findings`; they do not affect `summary` or the lint exit code
- [x] 3.5 Suppress or downgrade to `info` lint hints those `E016`/`E018` diagnostics caused solely by the disabled executor/host, with a note that lint mode is static

### Acceptance criteria

- [ ] No shell command or IPC transport is ever spawned during a lint run (verified by a fixture whose payload would have an observable side effect)
- [ ] `E016`/`E018` from static mode never become hard lint failures and never appear in `findings`
- [ ] Other compiler diagnostics (e.g. `E002`, `E003`) are reported in `diagnostics` and printed distinctly from L### findings

## Task 4: Rule passes L001–L006 (ymx-lint)

- [x] 4.1 Build the declaration/reference graph from the loaded `Project` with all eight sources: `$name(...)`, `$name{...}`/`key$name:`, `from:`, rule-8 shortcuts, `${...}` math calls, `$name`/`$N` interpolation reads, shell payloads, and IPC alias calls
- [x] 4.2 L001 — unused component/template (zero incoming references; templates used via rule-5 chain; entry, `_test`, and hook targets are roots; builtins excluded; IPC aliases excluded — L006 only)
- [x] 4.3 L002 — unreachable component from entry (traverse roots and implicit template edges; cycles handled; distinct from L001)
- [x] 4.4 L003 — unused argument (unread slot in a component body; modifiers stripped; `from` forwards all slots)
- [x] 4.5 L004 — caller passes an argument the target never reads (per call site, using the L003 read analysis; skip unresolved/builtin/forwarding targets)
- [x] 4.6 L005 — shell call with interpolated payload (unescaped `$name`, `$N`, `${...}`, `$name(...)`, `$name{...}` in `sh`/`pw` payloads)
- [x] 4.7 L006 — IPC alias declared but never called (including transitively re-exported aliases; any call form counts as a call)
- [x] 4.8 Apply `allow` (suppress), `deny` (promote to `error`), and default `warning` severity to every emitted finding
- [x] 4.9 Apply the `fail_on` threshold when computing findings; all six rules remain advisory by default

### Acceptance criteria

- [ ] Each rule reports at the correct declaration or reference span with a useful `help` message
- [ ] Every rule has a negative case producing no finding
- [ ] Rule findings never alter compiler output

## Task 5: CLI `lint` subcommand (ymx-cli)

- [x] 5.1 Parse `ymx lint <path> [flags]`; resolve `<path>` like compile mode (directory → `main.main`) and never read stdin
- [x] 5.2 Wire `load_project` → `extract_options` → `extract_lint_config` → static check → `lint_project` → emit
- [x] 5.3 Implement `--deny`, `--allow` (repeatable/comma-separated L-codes) and `--fail-on <error|warning|info|none>`
- [x] 5.4 Implement `--format diagnostics|json` for lint (default `diagnostics`); reject other format values with exit 2
- [x] 5.5 Accept `--entry`, `--plain`, `--plain-template`, `--max-depth`, `--allowed-backends`, `--allowed-ipc`; treat `-c`, `--test`, `--watch`, `--output`, `--pretty`, `--no-exec`, and `--no-ipc` as usage errors or implied no-ops per the spec
- [x] 5.6 Exit 0 when no emitted finding meets `fail_on`; 1 when one does or when load/option resolution fails; 2 for usage errors

### Acceptance criteria

- [x] `ymx lint <project>` prints findings in diagnostics format and exits 0 with default config on advisory warnings
- [x] `ymx lint <project> --deny L001` (or `_ymx.lint.deny: [L001]`) exits 1 when an L001 finding exists
- [x] `ymx lint <project> --fail-on none` exits 0 on findings alone
- [x] A load/option failure exits 1; a missing path or bad flag exits 2
