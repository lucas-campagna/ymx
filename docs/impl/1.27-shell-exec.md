# 1.27 — Shell execution builtins (`$sh`, `$pw`)

## Task 1: Core types — `CommandExecutor` trait and related types (ymx-core)

- [x] 1.1 Define `ExecOutput { exit_code: i32, stdout: String }` in ymx-core
- [x] 1.2 Define `ExecError { UnknownBackend(String), SpawnFailed(String) }` in ymx-core
- [x] 1.3 Define `pub trait CommandExecutor: Send + Sync { fn execute(&self, backend: &str, command: &str) -> Result<ExecOutput, ExecError>; }` in ymx-core
- [x] 1.4 Add `allowed_backends: Option<Vec<String>>` and `executor: Option<Arc<dyn CommandExecutor>>` fields to `Options` struct

### Acceptance criteria

- [x] `ExecOutput`, `ExecError`, `CommandExecutor` compile with no I/O imports in ymx-core
- [x] `Options` carries the two new fields with correct defaults (None, None)

## Task 2: Front-matter parsing — `allowed_backends` (ymx-config)

- [x] 2.1 Add `allowed_backends: Option<Vec<String>>` to `CliOverrides`
- [x] 2.2 Parse `allowed_backends` from `_ymx` YAML front-matter in `extract_options`
- [x] 2.3 Apply precedence: CLI `--allowed-backends` > entry-file `_ymx.allowed_backends` > engine default (all)
- [x] 2.4 Validate: each entry must be a non-empty string; invalid → E010

### Acceptance criteria

- [x] `_ymx: { allowed_backends: [sh] }` produces `Options.allowed_backends = Some(vec!["sh".into()])`
- [x] Absent `_ymx.allowed_backends` produces `Options.allowed_backends = None` (all allowed)
- [x] Invalid front-matter values emit E010

## Task 3: Parser — `$<backend>{...}` value expressions and property-key shorthand (ymx-core)

- [x] 3.1 Recognize `$<identifier>{...}` in value position as a new IR node type (executor call) distinct from `${...}` (math) and `$name(...)` (component call)
- [x] 3.2 Recognize `$<identifier>` suffix on any property key (including template keys) as executor shorthand — strip suffix, wrap value in executor call node
- [x] 3.3 Validate: the identifier must be a valid executor name `[A-Za-z_][A-Za-z0-9_]*`; invalid → E010
- [x] 3.4 Handle nested interpolation inside the command string (reuse existing string interpolation logic)

### Acceptance criteria

- [x] `$sh{echo hi}` parses to an executor call node with backend="sh", command="echo hi"
- [x] `$pw{Get-Content x}` parses to backend="pw", command="Get-Content x"
- [x] `main$sh: echo hi` parses identically to `main: $sh{echo hi}`
- [x] `$box$sh: echo $name` parses identically to `$box: $sh{echo $name}`
- [x] `${sh{...}}` (math containing executor) is NOT confused with `$sh{...}` — the math `${` takes precedence when `sh` is followed by `{` inside `${...}`
- [x] `$123{...}` (identifier starting with digit) is E010

## Task 4: Resolver — executor call evaluation (ymx-core)

- [x] 4.1 During property resolution (step 1 of rule 11), when encountering an executor call node: interpolate the command string (resolve `$name`, `$0`, `${...}` inside it)
- [x] 4.2 Enforce `allowed_backends`: if `opts.allowed_backends` is `Some` and the backend is not in the list → E016
- [x] 4.3 If `opts.executor` is `None` → E016 (executor not provided)
- [x] 4.4 Call `executor.execute(backend, interpolated_command)`
- [x] 4.5 On `ExecError::UnknownBackend` or `ExecError::SpawnFailed` → E016
- [x] 4.6 On success → return `Value::Object({ "exit_code": Value::Int(output.exit_code), "stdout": Value::String(output.stdout) })`
- [x] 4.7 Scalar interpolation inside command: Int renders as decimal, Float per render_f64, Bool as "true"/"false", Null as "null", String as-is. Array/Object as command argument → E011

### Acceptance criteria

- [x] `$sh{echo hello}` with StdExecutor → `{exit_code: 0, stdout: "hello\n"}`
- [x] Non-zero exit code returned in result (not an error): `$sh{exit 1}` → `{exit_code: 1, stdout: ""}`
- [x] Missing executor (`None`) → E016 diagnostic
- [x] Unknown backend → E016 diagnostic
- [x] Disallowed backend (not in allowed_backends) → E016 diagnostic
- [x] `$sh{echo $name}` with `name="world"` → command "echo world" → `{exit_code: 0, stdout: "world\n"}`
- [x] `$sh{echo ${x + 1}}` with `x=5` → command "echo 6" → `{exit_code: 0, stdout: "6\n"}`

## Task 5: Default executor — `StdExecutor` (ymx-lib)

- [x] 5.1 Implement `StdExecutor` in ymx-lib: maps "sh" → `sh -c`, "pw" → `pwsh -c` (or `powershell -Command` on Windows)
- [x] 5.2 Spawn the command via `std::process::Command`, capture stdout
- [x] 5.3 Map io::Error to `ExecError::SpawnFailed`
- [x] 5.4 Provide a convenience `compile_with_executor` (or set executor on Options before calling compile) so library users get shell execution by default

### Acceptance criteria

- [x] `StdExecutor` implements `CommandExecutor`
- [x] `StdExecutor.execute("sh", "echo hi")` → `Ok(ExecOutput { exit_code: 0, stdout: "hi\n" })`
- [x] `StdExecutor.execute("pw", "Write-Output hi")` → `Ok(...)` on systems with pwsh
- [x] `StdExecutor.execute("ruby", "puts 1")` → `Err(UnknownBackend("ruby"))`
- [x] ymx-core has no new I/O imports (std::process, std::fs, etc.)

## Task 6: CLI integration (ymx-cli)

- [x] 6.1 In the orchestration pipeline, after `extract_options`, set `opts.executor = Some(Arc::new(StdExecutor))`
- [x] 6.2 Add `--allowed-backends <list>` CLI flag (comma-separated) that overrides `_ymx.allowed_backends`
- [x] 6.3 Add `--no-exec` CLI flag that sets `opts.executor = None` (disables shell execution entirely)

### Acceptance criteria

- [x] `ymx file.yml` with `$sh{echo hi}` works out of the box (StdExecutor injected)
- [x] `ymx file.yml --no-exec` with `$sh{echo hi}` → E016
- [x] `ymx file.yml --allowed-backends sh` restricts to sh only

## Task 7: Diagnostic E016 (ymx-core)

### Acceptance criteria

- [x] All four E016 variants render correctly with file/line/col/component
- [x] E016 is documented in the diagnostic codes table in PRD.md
