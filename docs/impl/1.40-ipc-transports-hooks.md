# 1.40 — IPC transports, structured mode & hooks (rule 21 extended)

## Task 1: Socket transport (ymx-lib)

- [ ] 1.1 `transport: socket` with `path: "/path/to.sock"` → unix domain socket
- [ ] 1.2 `transport: socket` with `addr: "host:port"` → tcp socket
- [ ] 1.3 `external: true` → connect to existing socket (no spawn); `cmd`/`cwd`/`env` ignored
- [ ] 1.4 Unix socket: create socket, connect, use same framing/protocol machinery as pipe
- [ ] 1.5 TCP socket: `std::net::TcpStream`, connect, read/write
- [ ] 1.6 Session keyed by (project_root, alias, spec) — socket path/addr is part of spec hash
- [ ] 1.7 Teardown: close socket handle; `before_stop`/`after_stop` hooks still fire

### Acceptance criteria

- [ ] `transport: socket, path: "/tmp/test.sock", external: true` with a pre-started server works
- [ ] `transport: socket, addr: "localhost:9999", external: true` with a pre-started TCP server works
- [ ] Socket sessions persist and are reused across calls (stateful)

## Task 2: HTTP transport (ymx-lib)

- [ ] 2.1 `transport: http` with `url`, `method`, `headers`
- [ ] 2.2 `url` interpolation: `{$0}`/`{$name}` substituted with rendered argument values before each request
- [ ] 2.3 `query`: list of arg names placed in the URL query string (e.g. `query: [verbose]` → `?verbose=…`); remaining args go to body (or omitted for GET)
- [ ] 2.4 `body`: `all` (default) = render all args as per `mode` → body; `$0` = only positional arg; `name` = the named arg; `off` = no body (for GET)
- [ ] 2.5 `ok` status spec: default 2xx → success; non-matching → E018(StatusCode, body)
- [ ] 2.6 `external: true` implied for http (no process to spawn)
- [ ] 2.7 `request_timeout` applies to the full HTTP round-trip
- [ ] 2.8 Response: read body, apply `trim`/`parse`/`on_response` as usual; status code used for `ok` check
- [ ] 2.9 No `prelude`/`ready`/lifecycle hooks apply (stateless, no process)

### Acceptance criteria

- [ ] `transport: http, url: http://localhost:8080/rpc, method: POST, mode: json` with a JSON-RPC server works
- [ ] `url: http://api.example.com/users/{$0}` with $0=42 → GET /users/42
- [ ] `query: [verbose]` with verbose=true → ?verbose=true in URL
- [ ] Non-2xx response → E018 with response body as message
- [ ] `body: off` for GET produces no request body
- [ ] `parse: yaml` on JSON body → parses correctly (JSON ⊂ YAML)

## Task 3: JSON protocol and mode: json (ymx-core)

- [ ] 3.1 `protocol: json`: send one JSON value per line (newline-delimited JSON); read one line, parse as JSON
- [ ] 3.2 `protocol: jsonrpc`: send JSON-RPC 2.0 request (`{"jsonrpc": "2.0", "method": "...", "params": [...], "id": N}`); read one line, parse, match `id`, extract `result` or `error`
- [ ] 3.3 `mode: json`: serialize call arguments as one JSON object — positional args become integer keys `{0: v0, 1: v1, …}`, named args keep their string keys
- [ ] 3.4 For pure positional: `{0: v0, 1: v1}` — no array wrapper (uniform shape)
- [ ] 3.5 For pure named: `{name: value}` — no change from current JSON object form
- [ ] 3.6 `on_request` override: the component's result is used as-is (must be a JSON-serializable Value or String); the `mode` rendering is skipped

### Acceptance criteria

- [ ] `protocol: json` with `mode: text`: send raw string as a JSON string value `{"0": "hello"}`
- [ ] `protocol: json` with `mode: json`: send args as `{0: ..., name: ...}` object
- [ ] `protocol: jsonrpc` sends valid JSON-RPC 2.0 request; receives and parses JSON-RPC response
- [ ] `mode: json` with positional args only → `{0: "a", 1: "b"}` on wire
- [ ] `mode: json` with named args only → `{x: 1}` on wire
- [ ] `mode: json` with mixed args → `{0: "a", x: 1}` on wire
- [ ] `on_request: mycomp` with $0="hello" → mycomp called, its result sent

## Task 4: Component hooks — on_request, on_response, on_error (ymx-core)

- [ ] 4.1 `on_request`: during IPC call evaluation, before sending, call the named component with the full arg set (`$0`, `$name`); its result must be a String (or JSON Value if mode is json); that result replaces the `mode`-rendered payload
- [ ] 4.2 `on_response`: after receiving and trimming the raw reply, call the named component with `$0` = raw reply string; its result is the final `Value` (parse is skipped when hook is present, unless the hook itself returns a string that needs parsing — hook result is used as-is unless the hook raises)
- [ ] 4.3 `on_error`: on any `IpcError` during the call, call the named component with `$0` = error message string; if the hook returns a `Value`, that becomes the call result (success path); if the hook itself produces an error, the original `IpcError` stands
- [ ] 4.4 The hook component is resolved in the **current** namespace (same as regular component calls); it is a normal YMX component call (participates in depth counting; must not itself be an IPC component — no recursion)
- [ ] 4.5 Error if the hook component does not exist → E002 (at the call site of the hook, not the original IPC call)

### Acceptance criteria

- [ ] `on_request: upper` with `$0="hello"` → `upper` called with `0: hello` → returns `"HELLO"` → sent as "HELLO"
- [ ] `on_response: parse_json` with raw reply `{"a":1}` → `parse_json` called with `0: "{\"a\":1}"` → returns Object {a:1} → final Value is Object
- [ ] `on_error: fallback` with error "timeout" → `fallback` called with `0: "timeout"` → returns `"default"` → final Value is String "default"
- [ ] Hook component missing → E002
- [ ] Hook component recursion (IPC calling itself) → E008 or E002 as appropriate

## Task 5: Shell lifecycle hooks — before_start, after_start, before_stop, after_stop (ymx-lib)

- [ ] 5.1 `before_start`: before spawning the process, call `CommandExecutor::execute("sh", cmd)` with the shell string; wait for it to complete (exit code 0 = ok, non-zero → E018 HookFailed)
- [ ] 5.2 `after_start`: after successful spawn and `ready` satisfied, call the shell command; non-zero → E018 but does not prevent the session from continuing (warning? or hard fail — make it hard fail for consistency)
- [ ] 5.3 `before_stop`: before tearing down the session, call the shell command; non-zero → E018 but teardown proceeds
- [ ] 5.4 `after_stop`: after session teardown, call the shell command; non-zero → E018 but no session remains to care
- [ ] 5.5 These hooks use the **same `CommandExecutor`** as rule 19 — no separate I/O surface needed
- [ ] 5.6 `prelude` (already in 1.39) sends a string to the process stdin; hooks are separate (shell commands on the host, not the guest)

### Acceptance criteria

- [ ] `before_start: echo "building"` → runs before process spawn
- [ ] `before_start` failure → E018, process not spawned
- [ ] `after_start` failure → E018 but process is still used
- [ ] `before_stop` / `after_stop` run during session teardown
- [ ] Hooks run via CommandExecutor (same machinery as $sh)

## Task 6: Restart policy, envelope: full, stderr handling (ymx-core + ymx-lib)

- [ ] 6.1 `restart: on-failure`: after an `IpcError` on a call, mark the session dead; the next call to the same alias respawns a fresh session (new process, re-run prelude/ready)
- [ ] 6.2 `restart: never` (default): after an error, the session stays dead; next call → E018 again
- [ ] 6.3 `max_restarts`: cap how many times a session can be respawned; exceeded → E018 with message about max restarts
- [ ] 6.4 `envelope: full`: instead of returning the parsed payload directly, return `{stdout: String, stderr: String}` (rule 19 symmetry); `parse` still applies to `stdout`
- [ ] 6.5 `stderr: ignore` (default): stderr is not captured for response purposes (but still available for `envelope: full`)
- [ ] 6.6 `stderr: capture`: capture stderr to a string; if non-empty on call completion → available in `envelope: full.stderr`; non-empty alone does not cause an error by default
- [ ] 6.7 `stderr: fail`: if stderr is non-empty after a call → E018 with the stderr content as the message (useful for detecting stderr-output errors from compilers, etc.)
- [ ] 6.8 `error_pattern` (already in 1.39): checked after `parse`; if the (parsed or raw) reply matches the regex → E018 with the reply as message

### Acceptance criteria

- [ ] Session marked dead after error; next call respawns
- [ ] `max_restarts: 1` → after one respawn failure, second failure → E018 with max-restarts message
- [ ] `envelope: full` → result is `{stdout: "...", stderr: "..."}`
- [ ] `stderr: fail` with non-empty stderr → E018 with stderr content
- [ ] `error_pattern: "^ERR:"` on reply "ERR: something" → E018
